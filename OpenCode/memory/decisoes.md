# Decisões Técnicas e Regras de Negócio

## 1. Regras de Negócio Identificadas

### 1.1. Gestão de Usuários e Acesso
- **Identificação e Unicidade**: O e-mail do usuário é único no sistema. Tentativas de cadastrar um e-mail já existente geram recusa da operação.
- **Segurança da Senha**: A senha informada no cadastro deve possuir no mínimo 6 caracteres (`@Size(min = 6)` em `UsuarioRequestDTO`). Todas as senhas são armazenadas com hash gerado via BCrypt.
- **Papeis de Acesso (Roles)**:
  - `ROLE_USER`: Atribuído automaticamente no cadastro de novos cidadãos.
  - `ROLE_ADMIN`: Perfil para visualização geral de usuários e extração de métricas consolidadas.

### 1.2. Gestão de Ocorrências Urbanas
- **Criação de Ocorrência**:
  - Toda nova ocorrência é iniciada compulsoriamente com o status `StatusOcorrencia.PENDENTE`.
  - A data de criação é registrada automaticamente pelo ciclo de vida JPA (`@PrePersist` no método `aoCriar` ou no Service).
  - Valores padrão de localização: se o usuário não informar cidade ou bairro, o sistema aplica defaults configurados (`cidade = "Belem"`, `bairro = "Marco"`).
  - A ocorrência vincula-se ao usuário autenticado que efetuou a requisição.
- **Categorias Suportadas**:
  - `BURACO_NA_RUA` ("Buraco na rua")
  - `iLUMINAÇAO_PUBLICA` ("Iluminaçao publica")
  - `LIXO_ACUMULADO` ("Lixo acumulado")
  - `VAZAMENTO_DE_AGUA` ("Vazamento de agua")
  - `FALTA_SANEAMENTO` ("Falta saneamento")
  - `SINALIZAÇAO_DANIFICADA` ("Sinalizaçao danificada")
  - `OUTROS` ("Outros")
  - **Parsing Resiliente de Categoria**: A desserialização JSON em `Categoria.fromString` utiliza normalização NFD (removendo acentuações e caracteres especiais), conversão para caixa alta e substituição de hifens/espaços por sublinhados, garantindo tolerância a variações textuais do cliente.
- **Ciclo de Estados da Ocorrência**:
  - Estados: `PENDENTE` -> `EM_ANDAMENTO` -> `RESOLVIDO` / `CANCELADO`.
  - Mudanças de status devem ser auditadas gerando registros em `HistoricoStatus` com timestamp (`data_alteracao`) e vínculo com a ocorrência.

## 2. Escolhas Técnicas Adotadas

### 2.1. Autenticação e Segurança (Spring Security + JWT)
- **Sessões Stateless**: Desabilitação de gerenciamento de sessão HTTP (`SessionCreationPolicy.STATELESS`) e de proteção CSRF (`csrf.disable()`), ideal para APIs REST.
- **Token JWT HMAC-SHA**:
  - Assinatura simétrica configurada via `jwt.key` (chave base64) e expiração configurada via `jwt.expiration` (24h).
  - O filtro `JwtAuthFilter` intercepta requisições contendo `Bearer <token>` no header `Authorization`, valida a assinatura/expiração e popula o `SecurityContextHolder`.
  - Rotas públicas restritas: apenas endpoints `POST /auth/**` são abertos publicamente sem necessidade de token.

### 2.2. Modelagem de Dados e DTOs
- **Imutabilidade com Java Records**: Todos os DTOs (`request` e `response`) são definidos como `record`, trazendo imutabilidade nativa e concisão de código.
- **Padrão Builder**: Utilização de `@Builder` nos Records de resposta para criação fluente e legível.
- **Mapeamento Entidade -> DTO**: Métodos estáticos de fábrica `fromEntity(...)` definidos nos próprios Records de resposta (ex: `UsuarioResponseDTO.fromEntity(usuario)`, `OcorrenciaResponseDTO.fromEntity(ocorrencia)`).
- **Validação de Payload**: Uso intensivo de Bean Validation (`@NotBlank`, `@Size`) nos DTOs de entrada para falhar rápido antes de chegar à lógica de negócio.

### 2.3. Tratamento de Exceções
- Exceções específicas criadas estendendo `RuntimeException`:
  - `ResourceNotFoundException`: Para recursos não encontrados no banco.
  - `GeocodificacaoException`: Para falhas em serviços externos de geolocalização.
- *Observação técnica registrada*: A classe `GlobalExceptionHandler` estende `RuntimeException` no estado atual, sendo usada para lançar erros na camada de serviço. Foi identificada a necessidade técnica de transformá-la em `@RestControllerAdvice` com métodos anotados com `@ExceptionHandler` para retornar respostas padronizadas (status HTTP 400, 404, 401, 500 com JSON contendo timestamp e mensagem).

### 2.4. Persistência e Banco de Dados
- **Controle de Schema**: O Flyway gerencia o schema do banco, mantendo controle estrito das alterações através de scripts de migração sequenciais (`V1` a `V5`).
- **Estratégia de ID**: `GenerationType.IDENTITY` alinhada com `BIGINT GENERATED BY DEFAULT AS IDENTITY` no PostgreSQL.
- **Chaves Estrangeiras**:
  - Exclusão de usuário preserva o registro histórico da ocorrência desvinculando o autor (`ON DELETE SET NULL`).
  - Exclusão de ocorrência apaga todo o histórico de status associado (`ON DELETE CASCADE`).

### 2.5. Ambientes e Containerização
- **Multi-stage Dockerfile**: Separação clara entre ambiente de compilação (JDK 21) e de execução (JRE 21 Alpine), reduzindo a imagem final e aplicando segurança com usuário não-root `spring:spring`.
- **Orquestração**: `docker-compose.yaml` define dependência explícita da aplicação em relação ao banco via `condition: service_healthy` baseado no comando `pg_isready`.
